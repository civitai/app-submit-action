# civitai/app-submit-action

Submit a [Civitai App](https://developer.civitai.com/apps) for moderator review when you push a version tag.

The action installs the [`civitai` CLI](https://github.com/civitai/cli) and runs `civitai app submit`. It also sends a GitHub Actions OIDC token: GitHub signs this short-lived token, and it names the repository, tag and commit of the workflow run. Civitai checks it with GitHub and records that run with the submission.

Moderator review is unchanged. A submission from this action goes through the same review as one from your terminal.

## Usage

Copy this into `.github/workflows/release.yml` in your app's repository. The same file is at [`examples/release.yml`](examples/release.yml).

```yaml
name: Submit to Civitai

on:
  push:
    tags: ['v*']

jobs:
  submit:
    runs-on: ubuntu-latest
    permissions:
      contents: read   # check out the repository
      id-token: write  # let the action request a GitHub OIDC token
    steps:
      - uses: actions/checkout@v4
      - uses: civitai/app-submit-action@v1
        with:
          api-key: ${{ secrets.CIVITAI_API_KEY }}
```

Then:

1. **Add your API key as a repository secret.** In the repository, go to Settings → Secrets and variables → Actions → New repository secret. Name it `CIVITAI_API_KEY` and paste a Civitai API key from your account settings. Never put the key in the workflow file.
2. **Push a tag that matches the manifest version.** If `block.manifest.json` says `"version": "1.2.3"`, tag `v1.2.3` (or `1.2.3`):

   ```sh
   git tag v1.2.3
   git push origin v1.2.3
   ```

`permissions: id-token: write` is required. Without it GitHub gives the job no way to request the token, and the action stops with an error saying so.

If your app's bundle is generated by a build step, run that build before the action. Then point `path` at the directory that holds `block.manifest.json`.

## Inputs

| Input | Required | Default | What it is |
| --- | --- | --- | --- |
| `api-key` | yes | | Your Civitai API key, from a secret. |
| `path` | no | `.` | The app directory, the one holding `block.manifest.json`. |
| `cli-version` | no | `pinned` | The `civitai` CLI release to install: `pinned`, a tag such as `v0.1.142`, or `latest`. It must support `CIVITAI_GITHUB_OIDC_TOKEN`; the action checks this and stops if it does not. See [The CLI download](#the-cli-download) for what each choice trusts. |
| `audience` | no | `civitai.com` | The token audience. Civitai accepts only `civitai.com`, so leave it. |
| `base-url` | no | `https://civitai.com` | The Civitai site to submit to. |

## What it does, step by step

1. **Refuses anything but a tag push.** The run must be a `push` event for a tag ref. A branch push, a pull request, a manual `workflow_dispatch` or a `release` event fails at once, before anything is downloaded, even when it runs on a tag.
2. **Checks the tag against `block.manifest.json`.** The tag must be `v<version>` or `<version>`. The Civitai server checks this too, and refuses the submit when it does not match.
3. **Installs the CLI.** It downloads the `civitai` binary for the runner from the CLI's GitHub release and checks it against that release's `checksums.txt` (see [The CLI download](#the-cli-download)). Linux and macOS runners, x64 and arm64, are supported.
4. **Requests the token and submits.** It requests the OIDC token for the audience `civitai.com` and runs `civitai app submit --yes`. The API key goes in `CIVITAI_TOKEN` and the OIDC token in `CIVITAI_GITHUB_OIDC_TOKEN`. The token is masked in the log and never printed.

The submit then goes through the CLI's usual checks, such as the version and listing guards. Its output is the same as in your terminal.

## The CLI download

The checksum check catches a corrupted or truncated download. It does not prove who built the binary: the binary and `checksums.txt` come from the same GitHub release, and civitai/cli does not yet publish a signature or a build-provenance attestation for its binaries (`gh attestation verify` finds none). So:

- **`pinned` (the default) pins the bytes, not just the tag.** Each release of this action records one CLI version and the sha256 of its binary for every platform in [`scripts/pinned-cli.sh`](scripts/pinned-cli.sh), and refuses a download that does not match, even if the CLI release was later changed. A new CLI reaches you only when you move to a newer action version.
- **A tag such as `v0.1.142` pins the tag.** The binary is checked against that release's own `checksums.txt`. civitai/cli releases are immutable from v0.1.142 on, so a published release's files cannot be replaced; older releases could be.
- **`latest` trusts whatever civitai/cli last published.** Use it only if you accept that.

> 🔴 **Maintainers:** this version pins civitai CLI `v0.1.142`, the first release that sends `CIVITAI_GITHUB_OIDC_TOKEN`. To move the pin, set the version and all four sha256 values in `scripts/pinned-cli.sh` from that CLI release's `checksums.txt` (the bare-binary rows). CI's `release-pin` job fails a tag push while any of them is unset.

## What Civitai records, and what it does not mean

Civitai checks four things about the token:
- GitHub signed it for the audience `civitai.com`;
- it has not expired and has not been used before;
- it comes from a push of a tag that matches the manifest version;
- when the CLI reported a commit, the token's commit is that one.

Civitai then records the run's repository, tag, commit, workflow and run id with the submission. Moderators see it in review. For a public repository, the app's store page shows:

> Submitted by: GitHub Actions run of `owner/repo` @ `v1.2.3` (`abc1234`)

That line means a GitHub Actions run of that repository, for that tag, submitted this version. It does **not** mean Civitai built the app from that commit, or that the code has been reviewed for security. Your workflow builds and uploads the bundle, as you would from your terminal. Private repositories are never named on the store page.

A token that fails any check refuses the submit, with an error that says why. Rerun the workflow after fixing the cause, and it requests a fresh token.

## Versioning

Use `civitai/app-submit-action@v1`. Releases are tagged `v1.0.0`, `v1.0.1` and so on. The floating `v1` tag moves to the newest `v1.x.y` release, and a breaking change goes out as `v2`.

To pin exactly, use a commit SHA: `civitai/app-submit-action@<sha> # v1.0.0`.

### Maintainers: cutting a release

After the change is merged to `main`:

```sh
git tag -a v1.0.0 -m "v1.0.0" && git push origin v1.0.0
git tag -fa v1 -m "v1 -> v1.0.0" && git push -f origin v1
```

Moving `v1` is the only force-push this repository uses. It moves a tag, never a branch.
